# Складські команди TEST_USA

Наявний бот `@USAshop_test_bot` і налаштований чат TEST_USA shop залишаються одержувачами складських повідомлень.

## Команди

```text
+5Q0121407F       додати 1 шт.
+5Q0121407F 2     додати 2 шт.
-5Q0121407F       списати 1 шт.
-5Q0121407F 2     списати 2 шт.
```

Після знака допускається пробіл. Пошук точний за заводським артикулом або його експортним відповідником; регістр і дефіси не впливають. Якщо артикул належить кільком складським позиціям, бот надсилає кнопки вибору складу. Підтвердити вибір може автор команди. Невідомий артикул не створює порожньої товарної картки. Списання понад наявний залишок відхиляється.

Відповідь містить назву товару, склад, кількість до команди, зміну, залишок після команди, наявність і результат передачі на Prom. Якщо залишок уже змінила інша операція, бот також показує поточну кількість. При нулі сайт і Prom отримують «Немає в наявності».

## Запуск

1. Розгорнути оновлений образ сайту звичайним процесом Portainer. Нова таблиця `telegram_stock_commands` створюється чинною процедурою `seed_if_empty()` / `Base.metadata.create_all()`; існуючі таблиці не видаляються.
2. У **Кабінет → API → Складські команди Telegram** увімкнути приймання команд. Використовується вже налаштований Telegram chat ID; інші чати не можуть змінювати склад.
3. Для звичайних повідомлень `+АРТИКУЛ` / `-АРТИКУЛ` бот має бути адміністратором групи або мати вимкнений Privacy Mode. За ввімкненого Privacy Mode команду можна надіслати відповіддю на повідомлення цього бота. Див. [офіційне пояснення Telegram](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).
4. Перевірити, що обмін залишками Prom увімкнений у **Маркетплейси**. Бот використовує наявне зіставлення складського товару з карткою Prom. Однозначний відповідник із підтвердженим початковим залишком активується автоматично. Якщо початкові кількості або артикул різняться, бот повідомляє про необхідність звірки й не перезаписує віддалений залишок навмання.

Тестувати зміни кількості на окремій тестовій позиції. Усі автоматичні тести використовують підроблені Telegram/Prom та окремі бази даних, не реальний склад.

## Надійність

- Команда та зміна кількості фіксуються однією транзакцією. Повторна доставка того самого `update_id`, редагування або пересилання повідомлення не викликає повторного руху складу.
- Блокування рядка товару узгоджене з резервуванням замовлень сайту. Два одночасні списання не продають одну останню одиницю двічі.
- Отримання повідомлень виконується фоновим процесом сайту; PostgreSQL advisory lock допускає лише одного одержувача оновлень. Сторінка API читає збережений список чатів і не конкурує за `getUpdates`.
- Збережений offset передається Telegram тільки після фіксації транзакції. Старі повідомлення до першого ввімкнення не змінюють склад.
- На Prom передаються лише кількість і наявність. Підтвердження повертається після повторного читання реальної картки. Ціни, описи та фотографії не змінюються.
- Якщо Prom недоступний, кількість на сайті зберігається, відповідь показує очікування, а передача повторюється автоматично. Після успіху надходить підтвердження без повторного застосування `+` чи `-`.
- Існуючий webhook іншого обробника автоматично не видаляється; стан відображається у вкладці API.
