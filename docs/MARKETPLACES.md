# Маркетплейси: Prom і Автопро

Кабінет `/admin/marketplaces` об'єднує огляд, налаштування Prom, товари/залишки, замовлення, журнал та базове підключення Автопро. Старі посилання на прайси Автопро збережені. Публічна вітрина використовує ту саму базу й залишки.

## Запуск

1. Перед розгортанням створити резервну копію PostgreSQL, коду й фото. `seed_if_empty()` створює чотири нові таблиці через `Base.metadata.create_all`; існуючі дані не переносяться й не видаляються.
2. Перебудувати вебобраз із `requirements.txt` та перезапустити вебконтейнер звичайним розгортанням стека. Програма залишається одним процесом Waitress; при запуску додається фоновий scheduler маркетплейсів.
3. У Маркетплейси → Prom зберегти чинний токен. Перевіряється читання товарів і замовлень; токен шифрується Fernet із ключем, похідним від сильного серверного SECRET_KEY. Для старого встановлення з шаблонним SECRET_KEY автоматично створюється окремий випадковий ключ BACKUP_DIR/.marketplace-encryption.key з правами 0600. Він зберігається на постійному томі й додається до стандартного приватного бекапу в secrets/; після відновлення його потрібно повернути за тим самим шляхом. В HTML токен повторно не видається, у Git чи журналах не зберігається. За зміни SECRET_KEY токен потрібно зберегти повторно. Можливий також серверний PROM_API_TOKEN.
4. Дочекатися початкового читання каталогу й 30 днів історії. Зіставляються лише однозначні артикули без дублікатів на обох сторонах. Суперечливі залишки потребують явного вибору джерела.
5. Перевірити запис кнопкою «Перевірити запис без зміни кількості»: відправляється вже наявна, однакова в обох системах кількість, після чого виконується читання для підтвердження. Перевага надається вже нульовому товару. Перевірка не підміняє товар чи кількість тестовими значеннями.
6. Увімкнути автообмін. Типовий інтервал — 120 секунд; також доступні 5, 10 і 15 хвилин. Для Telegram використовуються наявні налаштування сайту; історичні замовлення не створюють розсилку.

## Облік

- Сайт веде спільний доступний залишок. Нове замовлення Prom резервує його; сайт передає актуальну кількість у Prom через `/products/edit`. Ціни Prom не змінюються.
- Початок обліку фіксується при підключенні. Старі замовлення імпортуються без повторного списання. Активне історичне замовлення можна окремо взяти в облік.
- Скасування повертає лише раніше створений цим замовленням резерв. Після відправки/виконання потрібне підтвердження фізичного повернення. Повторна доставка події або перезапуск процесу не повторюють списання.
- Редагування кількості враховує різницю старого й нового резерву. Якщо товарів не вистачає, старий резерв зберігається. Неоднозначні/неприв'язані позиції не підбираються за першим збігом артикула.
- Замовлення отримуються через `last_modified_from/to` із перекриттям 5 хвилин та пагінацією. Старіші знімки не повертають замовлення до минулого стану. Помилка окремого замовлення не блокує решту; його дані залишаються для повторної обробки.
- Ручна зміна кількості на Prom не перезаписується мовчки: розбіжність показується для звірки. Адміністратор може обрати кількість сайту чи Prom. Це свідоме узгодження, а не сліпе взаємне перезаписування.
- Для нуля відправляються `quantity_in_stock=0` та `presence=not_available`. Перевіряються `processed_ids`, `errors`, а потім фактична картка товару. Реальний Prom повернув HTTP 200, порожні processed_ids/errors/warnings при незмінній кількості. Цей результат приймається лише з повторним читанням; перевірка без змін має окремий індикатор і не позначається як підтверджена реальна зміна кількості. Різновиди з успадкованою наявністю можуть відхиляти таку зміну — помилка залишається в кабінеті.
- Кількість має бути цілою; грошові рядки Prom з UAH/грн та нерозривними пробілами розбираються окремо. Початкова сума UAH зберігається точно; для сумісності старого кабінету створюється USD-еквівалент за зафіксованим курсом сайту.

## Надійність і доступ

Адміністративні запити перевіряють авторизацію й CSRF. Відповіді кабінету мають `no-store`, `noindex` і `no-referrer`. API працює лише з фіксованим HTTPS-хостом Prom, не пересилає токен при редиректах і не виводить його у повідомленнях помилок. Глобальний PostgreSQL advisory lock та локальний lock запобігають паралельним циклам обміну; помилки API відкладають наступну спробу. Абсолютні кількості й повторне читання дозволяють відновитися після непевного результату запису.

Облік резервів використовує блокування рядків PostgreSQL. Для кількості застосовується FOR NO KEY UPDATE, сумісний з FK-посиланнями нових позицій замовлення. Це перевірено на одночасному продажі останньої одиниці. Оновлення запасів очищує кеш вітрини.

Події та завдання зберігаються в базі. Сповіщення Telegram мають чергу й обмежені повтори; за непевного мережевого результату Telegram не надає гарантії рівно однієї доставки. Основний запис події в кабінеті має унікальний ключ.

## Автопро

Базові налаштування зберігають акаунт, примітку та необов'язковий зашифрований ключ. Прайси доступні з цього ж розділу. Підключення API замовлень не імітується: робочий акаунт раніше повернув `Partner is not registered`. Автооновлення Автопро залишається окремим каналом сайт → Автопро; обробка останньої проданої позиції потребує перевірки, описаної в AVTOPRO_AUTOUPDATE.md.

## Перевірки перед розгортанням

- 65 цільових тестів пройшли: 29 нових перевірок Prom/кабінету, 3 тести реальної конкуренції на ізольованому PostgreSQL та 33 наявні перевірки пошуку, Avtopro-фідів і Google Ads.
- Повний набір: 89 тестів, одна стара помилка `test_catalog_canonical_normalization` (localhost у редиректі проти усапартс-домену поза контекстом запиту), один пропуск. Окремий запуск незміненого HEAD підтвердив ту саму помилку до цих змін. Код каталогу заради цього не змінювався.
- Перевірено всі шість сторінок у браузері; сторінка з непорожніми замовленнями та екран 390 px перевірені окремо. Таблиці прокручуються всередині контейнера.
- Перед розгортанням на сервері створено й перевірено `/app/backups/pre_marketplaces_20261102T215520Z.zip` (код, фото, database.dump). Старі архіви не видалялися.

Офіційні контракти: https://public-api.docs.prom.ua/.


У production шаблонний ключ сесії замінюється постійним випадковим BACKUP_DIR/.session-secret.key (0600); початковий перехід вимагає повторного входу в кабінет. Він включений у приватний повний бекап. Сильний чинний SECRET_KEY не змінюється. Для Git-стека pull_policy: build змушує зібрати актуальний код, а не використати попередній кешований образ.

Бойовий початковий імпорт: 3580 товарів Prom, 3316 зіставлених позицій, 3188 готових до обміну, 392 на звірку/зіставлення, 43 історичні замовлення. Telegram уже налаштований: серверна перевірка getMe/getChat підтвердила доступ бота й чату. Тестові повідомлення не надсилались. Кабінет також явно показує відсутність налаштувань для нових встановлень. Автообмін опитує API з інтервалом, тому не забезпечує миттєвого резервування на зовнішньому маркетплейсі. Помилки резерву зберігаються для менеджера, склад не йде в мінус.

Відсутня кількість Prom (null) не трактується як нуль. Така позиція потребує явного вибору залишку сайту; дія «Взяти з Prom» недоступна. Після вибору сайту кількісний облік Prom ініціалізується з перевіркою результату.

03.11.2026 увімкнено автообмін кожні 120 секунд, оновлення залишків і наявний Telegram. За вибором власника 128 початкових розбіжностей залишено для ручної звірки; 264 картки очікують однозначного зіставлення. Підтверджена перевірка API без зміни кількості. Реальну зміну/перехід до нуля в Prom штучно не створювали. Після налаштування перевірено приватний архів /app/backups/marketplaces_configured_20261102T222312Z.zip (28855740 байтів), що містить БД, код, фото та постійний ключ.
